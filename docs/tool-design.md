# Config tool: design

> **Design agreed on 21 Oct 2026.** The tool is **lodestar** (typed `lds`) and
> the work laptop is **wandersail**. The decisions are summed up in
> [§13](#13-decisions).

lodestar replaces aconfmgr, chezmoi, `just` and the helper scripts in `scripts/`
with one Go program. It manages both machines from this repo: packages, system
files, services, firewall, boot, `$HOME`, KDE settings, and the install from the
live USB.

## 1. Why replace the current setup

- **Two tools, three models.** The system uses aconfmgr's bash DSL and `$HOME`
  uses chezmoi's file naming (`private_dot_config`, `run_onchange_after_…`).
  `just` and seven scripts glue the two together.
- **The interesting parts are already custom.** KDE keys, Readest keys, local
  packages, the `limine.conf` merge and mouse acceleration are all scripts,
  because neither tool covers them.
- **Install and apply are two code paths.** `scripts/aconf-packages` and
  `install/lib.sh` re-implement aconfmgr's DSL with stub functions, because
  aconfmgr can't evaluate the config for another host or apply it into `/mnt`.
- **Everything needs root.** aconfmgr reads the filesystem as root even to
  diff, so `just diff` and `just drift` always ask for a password, and Claude
  can never check drift.

## 2. Goals and non-goals

Goals:
- One description of each machine, in plain data files that are readable
  without knowing the tool.
- `lodestar plan` shows exactly what `lodestar apply` would change, without root.
- `lodestar apply` asks for the password once.
- `lodestar drift` lists everything on the machine that the repo doesn't know
  about, and `lodestar prune` removes undeclared packages.
- `lodestar install <host>` turns a blank disk into that host from the live USB.
  Nothing is typed but passwords.
- It is installed as a package, runs from any folder, and has fish completion.

Non-goals:
- **Not Nix.** There are no generations, no store and no expression language.
  Rollback is snapper's job, and lodestar takes a snapshot pair around each apply.
- **One distro, one user, local only.** No other distros, no other users, no
  remote deploys.
- **No package building of its own.** Repo packages go through pacman, AUR
  packages through yay, and local PKGBUILDs through makepkg.

## 3. Hosts and modules

### Layout

```
hosts/
  menadion/
    host.yaml         modules, variables, install settings, host-only settings
    system/  home/    host-only files
    windows/          the Windows side of the dual boot (not installed)
  wandersail/
    host.yaml
modules/
  mutectl/
    module.yaml       what the module declares
    system/           files for /       (system/etc/… is /etc/…)
    home/             files for $HOME   (home/.config/… is ~/.config/…)
    pkg/              a local package: its PKGBUILD and sources
  mpv/
    module.yaml
    config/           mpv's config: linked to ~/.config/mpv, used by Windows too
    windows/          Setup-Mpv.ps1
  lodestar/
    module.yaml
    pkg/              lodestar's Go source and PKGBUILD
    test/             the container and VM tests
  base/  desktop/  kde/  laptop/  dev/  docker/  …
schema/               JSON Schemas generated by lodestar, for completion in VS Code
.vscode/              settings.json: the schemas, and editor tab names
docs/
install.sh            run from the live USB: builds lodestar, starts the install (§9)
```

- **Hosts and modules are folders with the same layout.** The folder name is
  the hostname or the module name, and the YAML file is `host.yaml` or
  `module.yaml`. A host is a module plus the settings only a host has:
  `modules`, `vars`, `user` and `install`.
- **Only `system/` and `home/` are installed.** A file's place under them is
  its place on disk: `modules/base/system/etc/locale.conf` is
  `/etc/locale.conf`, and `modules/git/home/.gitconfig` is `~/.gitconfig`.
  Names are not encoded. A `.tmpl` suffix marks a template
  ([§5](#5-templates-facts-and-secrets)).
- **`pkg/` holds the module's local package.** Including the module installs
  it, so everything about a tool (code, PKGBUILD, unit, shortcuts, ports) sits
  in one folder. A tool with a repo of its own is pointed to from
  `module.yaml` instead ([§4](#packages)).
- **Anything else in the folder is not installed.** Links and hooks use it,
  like mpv's `config/`. Paths written in a `host.yaml` or `module.yaml` are
  relative to its own folder.
- **lodestar is a module like your other tools.** `modules/lodestar/pkg/` holds
  its Go source next to its PKGBUILD, and `test/` its container and VM tests.

### A host

The installer writes `/etc/hostname` from the folder name.

```yaml
# hosts/wandersail/host.yaml
modules:
  - base
  - desktop
  - kde
  - laptop
  - dev
  - docker
  - mutectl
  - spotify-vol
  - work

vars:                      # available to templates
  email: nicolasromain0@gmail.com

user:
  name: romain
  shell: /usr/bin/fish
  groups:
    - wheel
    - docker
    - input

install:                   # read only by `lodestar install` (§9)
  disk: nvme-SK_hynix_BC901_HFS512GEJ9X108N_<serial>   # /dev/disk/by-id name; any other disk is refused
  esp: 4GiB
  encrypt: true
  swapfile: 32GiB

# Anything a module can declare can also go here, and it wins over the modules.
kde:
  kscreenlockerrc:
    Daemon:
      Timeout: 6
```

### A module

```yaml
# modules/kdeconnect/module.yaml
packages:
  - kdeconnect
  - sshfs                  # browse the phone's files

firewall:
  tcp:
    - 1714-1764
  udp:
    - 1714-1764
```

```yaml
# modules/mutectl/module.yaml   (pkg/ holds the PKGBUILD and the Go source)
services:
  - mutectl.service

shortcuts:
  - name: Mute
    keys: Meta+É
    run: mutectl mute
```

### Merge rules

- **Sets are unions.** Packages, services, firewall ports and groups from every
  module are combined.
- **Single values are overridden.** A KDE key or a variable takes the value
  from the last module in the host's list that sets it, and the host file wins
  over all of them. `lodestar plan --explain <key>` says where a value came from.
- **Files can't collide.** Two modules providing the same file is an error. A
  host replaces a module's file by putting its own at the same path in its own
  `system/` or `home/`.

### Editing in VS Code

- **Schema from the code.** `lodestar schema` generates JSON Schemas from
  lodestar's own Go types into `schema/`, so the schema can't drift from what
  lodestar reads. `.vscode/settings.json` maps `hosts/*/host.yaml` and
  `modules/*/module.yaml` to them for Red Hat's YAML extension; no file needs a
  header comment.
- **What you get:** completion of keys and allowed values, descriptions on
  hover, and errors on unknown keys or wrong types as you type.
- **Readable tabs.** Every module file is called `module.yaml`, so
  `.vscode/settings.json` also names editor tabs after the folder
  (`workbench.editor.customLabels.patterns`): `mutectl (module)`,
  `wandersail (host)`.
- **KDE keys too** (step 2 of §11). KDE describes many of its settings in
  `.kcfg` files, with types and allowed values: 85 files on the laptop, 93
  settings in `kwin.kcfg` alone. lodestar adds them to the schema. Settings
  KDE doesn't describe (shortcuts, panel layout) get no completion.
- **YAML's traps are closed.** Every field is read into a declared type, and an
  unknown key is an error with its file and line. KDE values are kept exactly
  as written, so `no` stays `no` and `0440` stays `0440`.

## 4. What can be declared

| Resource | Declared as | When removed from the repo | Drift finds |
|---|---|---|---|
| Packages | `packages:`; a module's `pkg/` or `pkg:` | stays until `lodestar prune` | explicit packages not declared; declared ones missing |
| System files | `system/` | the package's original is restored, or the file is deleted | modified package files, unowned files in `/etc` |
| Home files | `home/` | deleted if unchanged since lodestar wrote it | managed files edited on the machine |
| Units | `services:`, `user-services:` | disabled | units enabled by hand (not by a package preset) |
| User and groups | `user:` | left as is | groups the user has beyond the declared ones |
| Firewall ports | `firewall:` | closed | — (lodestar generates the whole ruleset) |
| KDE keys | `kde: <file>: <group>:` | key deleted, so KDE's default comes back | live value differs; keys changed in System Settings since the last apply |
| KDE lists | `breeze-exceptions:`, `window-rules:` | entry removed, the rest renumbered | entries added in the GUI |
| Shortcuts | `shortcuts:` | removed | — |
| JSON keys | `json:` | left (no default is known) | live value differs |
| Hooks | `hooks:` | — | — |

### Packages

- **`packages:`** lists repo and AUR packages. A name found in the sync
  databases is a repo package; anything else is an AUR package, built by yay.
  The plan shows which.
- **Local packages** are built with makepkg from a PKGBUILD. They are not
  listed: including their module installs them. The PKGBUILD is either:
  - **in the module's `pkg/`**, for tools whose code lives in this repo
    (mutectl, spotify-vol, backdrop, logi-smartshift, lodestar);
  - **in the tool's own repo**, for tools that have one (awpro,
    whatdidhesay):
    ```yaml
    # modules/awpro/module.yaml
    pkg:
      git: git@github.com:romain-ncls/awpro.git
      ref: v0.3.0                 # a tag or commit pins it; a branch follows it
      path: packaging/arch        # where the PKGBUILD is in that repo
    ```
    lodestar fetches that ref with your git credentials into
    `~/.cache/lodestar/src/` and runs makepkg there. To update, change `ref`.
    While you work on a tool, `git:` can point at your local checkout.
- **The PKGBUILD should build from the fetched source,** so the ref alone
  decides the version. awpro's PKGBUILD downloads a release tarball with a
  checksum instead, and someone has to bump both at each release: on awpro's
  `main` it still says 0.2.1, while the latest release is v0.3.0.
- **Private repos during install.** The new machine has no SSH key yet, so
  `lodestar install` skips the packages it can't fetch, and the plan lists
  them. The first `lodestar apply` after your key is back builds them.
- **When a local package is rebuilt:** its `pkg/` folder changed (lodestar
  keeps the hash in its state, not in the package), its `ref` changed, a
  followed branch moved, or a library it links to went away (below).
- **Names must not collide with the AUR.** yay upgrades any installed package
  whose name it finds in the AUR with a higher version, even a local one.
  `lodestar check` warns when a local package has the name of an AUR or repo
  package. That is why `logi-wheel` became `logi-smartshift`: an unrelated
  AUR package for racing wheels has the first name.

### Updates

- **One command.** `lodestar upgrade` (`lds up`) runs `yay -Syu` with the local
  packages excluded, then rebuilds the local packages that need it (above).
- **No pacman hook of our own.** A pacman hook runs as root while pacman holds
  its database lock, so it can't build or install anything; it could only warn.
  The useful warning already exists: `rebuild-detector` (Arch repos) warns
  after each transaction when a package links to a library that is gone. The
  base module installs it, and `lodestar upgrade` uses its `checkrebuild` to
  find what to rebuild.
- **Few of your tools are concerned.** The Go tools and awpro are static
  binaries, so library upgrades never break them. whatdidhesay (Rust with
  Vulkan) is the one that can need a rebuild.

### Files

- **System files** are owned by root with mode 644, or 755 if the file is
  executable in git. Exceptions go in `module.yaml`:
  ```yaml
  files:
    /etc/sudoers:
      mode: "0440"                # quoted: unquoted, YAML reads a number (the editor flags it)
      check: "visudo -cf {}"      # runs on the new file before it replaces the live one
  ```
- **Home files are copied, not linked.** That way an app can't write into the
  repo by accident, and drift shows edits. Links are opt-in, for things you edit
  in place:
  ```yaml
  # modules/mpv/module.yaml
  files:
    ~/.config/mpv:
      link: config                # relative to the module folder
  ```
- **Follow-ups.** Built-in follow-ups run when a file they depend on changes:
  `locale-gen`, `udevadm control --reload` with a trigger,
  `systemctl daemon-reload`, `limine-mkinitcpio` (after `mkinitcpio.conf` or
  `kernel/cmdline`), and `sysctl --system`. Any other follow-up is set with
  `then: …` on the file.

### Services

- `services` enables system units with `systemctl enable`.
- `user-services` enables user units for every user with
  `systemctl --global enable`.

Both also work from the installer's chroot. A unit drop-in is just a file, such
as `system/etc/systemd/system/languagetool.service.d/port.conf`.

### Firewall

Modules declare the ports they need, and lodestar generates one nftables ruleset
from them. Incoming traffic is dropped except:
- established connections
- loopback and ICMP
- traffic from Docker's bridges
- the declared ports

The ruleset lives in its own table. lodestar replaces that table with
`destroy table` followed by its definition, and never runs `flush ruleset`, so
Docker's own tables are left alone.

Caveat: Docker handles ports published with `-p` before this filter sees them,
so a `-p 5432:5432` container is reachable from the network anyway. Bind dev
containers to `127.0.0.1:`.

### KDE

- **Whole files or keys.** If KDE only reads a file, the module keeps the whole
  file: themes (colour schemes, Plasma style, global theme, icons, cursors),
  Konsole profiles, `.desktop` entries, KWin scripts and wallpaper plugins. If
  KDE also writes a file (the `*rc` files in `~/.config`), the module keeps only
  the keys you chose. Those files mix settings with KDE's state (window sizes,
  tiling layouts, last-used tools), machine-specific values (input devices,
  screen names) and many apps' settings in one file. A whole copy would reset
  that state on every apply, and couldn't be shared between hosts.
- **Keys** are set by file, group and key:
  ```yaml
  kde:
    kwinrc:
      Windows:
        Placement: Centered
    powerdevilrc:
      AC/Display:                 # nested groups separated by /
        DimDisplayWhenIdle: false
  ```
  lodestar reads KDE files with its own parser, so drift stays fast with no
  process per key. It writes with `kwriteconfig6`, KDE's own library, which
  changes only the given key and handles KDE's escaping. The plan says which
  changes trigger a KWin reconfigure (done automatically) and which need a new
  login.
- **Lists.** Breeze window exceptions and KWin window rules are numbered
  groups, and two modules can't share fixed numbers: home-arch's mpv exception
  is "Exception 0", which is the Konsole rule on the laptop. So lodestar owns the
  whole list. Each module adds entries, and lodestar numbers them and removes
  leftovers.
  ```yaml
  breeze-exceptions:              # in modules/mpv
    - pattern: mpv
      hide-title-bar: true
      border-size: 0
  ```
- **Shortcuts** live in the module that provides the command. A host gets the
  shortcuts of the modules it includes, which is how a shortcut is shared or
  kept to one host. Custom commands become KDE's own `net.local.*.desktop`
  entries, so System Settings lists them as usual. Built-in actions can be
  rebound too:
  ```yaml
  shortcuts:
    - component: kwin
      action: Window Maximize
      keys:
        - Meta+Up
  ```
- **Capturing changes made in System Settings.** At each apply, lodestar saves
  a snapshot of the KDE files. `lodestar kde review` lists the keys changed
  since then and asks what to do with each one:
  - **keep** it: lodestar adds it to the module or host you pick
  - **ignore** it: it goes in that module's `kde-ignore:` list and is never shown again
  - **undo** it: lodestar writes the old value back

  `lodestar drift` counts these keys too. A built-in list hides KDE's own state
  (window sizes, tiling layouts, recent files, migration markers). That list
  will need tuning in the first weeks: whatever it misses shows up as noise.
- **Which key does this checkbox set?** `lodestar kde watch` answers that one
  question. It snapshots the KDE files, waits while you change one setting,
  then prints the changed keys as YAML.
- **Not covered at first: the panel layout.** Plasma stores it as numbered
  sections tied to screen numbers, so neither keys nor whole files fit. Plasma
  can script panels through `plasmashell`; that can come later.

### JSON keys

Some apps rewrite their own settings file, like Readest. For those, lodestar
merges the chosen keys into the file:

```yaml
json:
  - path: ~/.config/com.bilingify.readest/settings.json
    merge: readest.json           # relative to the module folder
    unless-running: readest       # Readest overwrites the file when it exits
```

### Hooks

Hooks are the escape hatch for what isn't a file or a key, such as flat mouse
acceleration for every mouse or the KRDP certificate.

```yaml
hooks:
  - run: flat-mice                # a script in the module folder
    as: user                      # or root
    when: always                  # or changed: the module changed since the last run
```

## 5. Templates, facts and secrets

Files ending in `.tmpl` are Go templates. They can use:
- `.host`, `.vars.*` and `.user.*`.
- **Facts** read from the machine at apply time: `fact "root-luks-uuid"`,
  `fact "esp-uuid"`, `fact "resume-offset"`. `/etc/fstab` and
  `/etc/kernel/cmdline` are templates, so the repo holds no UUIDs and a
  reinstall needs no edit to the repo.
- `file "~/.ssh/id_ed25519.pub"`, which is empty if the file is missing. The
  git `allowed_signers` file uses it.
- `bitwarden "item" "field"`. lodestar runs `bw unlock` the first time a template
  needs a secret, and keeps the session only for that run. The repo never holds
  secrets, encrypted or not.

## 6. Commands

| Command | Root | What it does |
|---|---|---|
| `lodestar plan` | no | shows what `apply` would change |
| `lodestar apply [--system \| --home]` | one prompt | makes the machine match the repo |
| `lodestar drift` | no¹ | lists everything the repo doesn't know about; exits 1 if there is anything |
| `lodestar prune` | one prompt | removes undeclared explicit packages and orphans, after showing the list and asking for confirmation |
| `lodestar upgrade` | one prompt | `yay -Syu` without the local packages, then rebuilds the local packages that need it ([§4](#updates)) |
| `lodestar add <path> [--to <module>]` | no | copies a live file into a module |
| `lodestar kde review` | no | keep, ignore or undo each KDE key changed since the last apply ([§4](#kde)) |
| `lodestar kde watch` | no | shows which keys one change in System Settings sets ([§4](#kde)) |
| `lodestar check [--host <h>]` | no | validates a host's config without reading the machine; CI runs it for every host |
| `lodestar schema` | no | regenerates the JSON Schemas in `schema/` |
| `lodestar install <host>` | live USB | see [§9](#9-install) |

¹ A few root-only files (`/etc/sudoers`, `/etc/sudoers.d/`) can't be read.
Drift says so, and `sudo lodestar drift` checks them too.

lodestar finds the repo at `~/dotfiles`, or at `$LODESTAR_REPO`. It takes the host
from the hostname, or from `--host`. The package ships fish completions and
the fish abbr `lds`, so `lds plan` expands to `lodestar plan`.

## 7. How apply runs

1. **Plan, as you.** lodestar loads the config, reads the machine, computes the
   plan and shows it. `plan` stops here.
2. **Password, once.** lodestar runs `sudo -v` and keeps it alive for the run.
3. **Pre-snapshot** with snapper.
4. **Repo packages, as root** (`pacman -S --needed`). Packages come before
   files, so pacman never finds an unowned file in its way.
5. **AUR and local packages, as you.** yay builds the AUR packages and makepkg
   the changed local ones. Installing them uses the cached sudo.
6. **System config, as root:** system files, units, user and groups, firewall,
   `limine.conf`, then the follow-ups.
7. **Post-snapshot** with snapper.
8. **Home, as you:** home files, KDE keys, lists and shortcuts, JSON keys,
   hooks. Then the KDE snapshot for `kde review`.

The root steps run as `sudo lodestar` with the plan passed on stdin, so the root
side does exactly what was shown. Claude can run `plan` and `drift`; `apply`
stays yours.

## 8. State and removal

lodestar records what it did in two state files: `/var/lib/lodestar/state.json` and
`~/.local/state/lodestar/state.json`. For each file it wrote, the record holds the
path, the hash and the module that declared it. The state also lists the KDE
keys lodestar set and the hashes of hooks and local packages. The KDE snapshot
for `kde review` sits next to it, in `~/.local/state/lodestar/kde/`.

The state is what lets lodestar remove something you deleted from the repo. It
also tells "you edited this on the machine" apart from "the repo changed".

- **System files.** If the file belonged to a package, the package's version
  comes back from the package cache. An unowned file is deleted.
- **Home files.** A file is deleted only if it is unchanged since lodestar wrote
  it. Otherwise the plan warns and leaves it.
- **Packages.** `apply` never removes packages. Trying something with
  `yay -S foo` is fine: `drift` lists it, and you either add it to a module or
  run `lodestar prune` to remove it.

## 9. Install

From the live USB:

```sh
loadkeys fr                                   # the live USB starts in US layout
iwctl station wlan0 connect "<SSID>"          # or plug in ethernet
curl -fsSL https://raw.githubusercontent.com/romain-ncls/dotfiles/main/install.sh | bash -s -- wandersail
```

No binary is published anywhere. `install.sh` builds lodestar on the live USB
from the repo:

1. **Safe to pipe.** The whole script is one function called on its last line,
   so a download cut halfway runs nothing.
2. **Room on the live USB.** The live system's writable space is a 256 MiB
   RAM disk by default, and git plus Go take about 300 MiB. The script enlarges
   it (`mount -o remount,size=2G /run/archiso/cowspace`).
3. **Tools.** `pacman -Sy archlinux-keyring git go`: the ISO has neither git
   nor Go, and an older ISO's keyring may reject today's packages.
4. **Repo.** It clones the repo over HTTPS into `/root/dotfiles`.
   `--branch <name>` picks another branch, for testing before a merge.
5. **Build.** `go build` makes `/root/lodestar`, a static binary.
6. **Hand over.** It runs `lodestar install wandersail --repo /root/dotfiles`
   with its input taken from the terminal (`</dev/tty`). Piped into bash, the
   script's input is the download itself: without the redirect, lodestar's
   questions and cryptsetup's passphrase prompt would read the rest of the
   script instead of your keyboard.

lodestar then does the rest:

1. **Checks.** lodestar checks that it is on the live USB, booted in UEFI mode,
   with a network connection. The disk must be the one named in
   `install.disk`. It shows the disk and asks you to type the hostname.
2. **Passwords, all at once.** The disk passphrase and your password (root
   gets the same), each typed twice. The rest runs unattended.
3. **Disk (wandersail).**
   - A GPT partition table.
   - A 4 GiB FAT32 ESP mounted at `/boot`. Limine reads only FAT, so kernels and
     snapshot kernels live there.
   - The rest as LUKS2. Inside it, btrfs with the subvolumes `@`, `@home`,
     `@snapshots`, `@var_log`, `@var_cache`, `@var_tmp`, `@var_lib_docker`
     and `@swap`. `@swap` holds a 32 GiB swapfile for hibernation.
4. **Facts.** The UUIDs and the swapfile's resume offset are measured on the
   new disk and saved in `/var/lib/lodestar/facts.json`, so `fstab` and the
   kernel command line (`rd.luks.name=…`, `resume_offset=…`) are right the
   first time, and later plans read the offset without root.
5. **Packages.** `pacstrap` installs the host's repo packages (with the repo's
   `pacman.conf`, for multilib).
6. **User, repo, snapper.** The user is created and the clone, with its
   history, is copied to `~/dotfiles`; links into the repo then point where
   it stays. Snapper's config is made, with `@snapshots` in place of its own
   subvolume.
7. **lodestar apply, inside the new system.** `arch-chroot` runs
   `lodestar apply --system`: the same code as on a running system, so the
   install is the plan of an empty machine. AUR and local packages are
   built as your user with a temporary sudo rule, removed whatever happens;
   yay is built first. The home part waits for the first login, where
   Plasma runs.
   - The initramfs gets the French keymap, so the passphrase prompt uses
     AZERTY.
8. **Boot.** `limine-install`, `limine-mkinitcpio`, then a second apply that
   merges the hand-written part of `limine.conf` and enrolls its hash.
9. **Passwords and remote.** The passwords are set, and the clone's remote is
   switched to the SSH URL, so pushing works once your key is set up.
10. **First boot.** Reboot, type the LUKS passphrase and log in. Run
    `lodestar apply` for the home side; it asks for the Bitwarden master
    password once. Then restore data from the backup.

You type only passwords: the LUKS passphrase, your user and root passwords,
the Bitwarden master password, and restic's. Rerunning the install is safe:
everything it writes is on the disk it formats.

## 10. Testing

- **Go tests** cover config merging, planning against a fake machine, the KDE
  parser and templates.
- **CI** runs `lodestar check` for every host on each push, which catches a broken
  config before it reaches a machine. It publishes nothing, and can be dropped.
- **Arch container.** Docker on the laptop applies the system side into a
  throwaway Arch root.
- **VM.** QEMU with UEFI and a blank virtual disk, on the laptop:
  1. Boot the Arch ISO with `script=`, so it runs `install.sh` unattended,
     with test passphrases. The test goes through the same script as the real
     install.
  2. Reboot, unlock the disk and reach the login screen.
  3. Run `apply` and take a screenshot.

  The VM runs under a memory cap, one at a time. Passing this test is the gate
  before touching the real disk.

## 11. Getting there

1. **Core:** config loading; `plan`, `apply`, `drift` and `prune` for packages,
   files, services and the user; templates, Bitwarden and state.
2. **The rest of the resources:** KDE keys, lists, shortcuts, `kde review`,
   `kde watch` and `.kcfg` completion, then JSON keys, hooks, local packages,
   the firewall and Limine.
3. **Port home-arch:** move `system/`, `home/`, `.kde/`, `pkg/`, `scripts/`,
   `mpv/` and `windows/` into hosts and modules. Then
   `lodestar check --host menadion` should pass, and the result should match
   what menadion has.
4. **The wandersail host:**
   - the inventory items
   - your tools as modules with a `pkg/` (with `qdbus` changed to `qdbus6`),
     and awpro and whatdidhesay through `pkg: git:` (their PKGBUILDs building
     from source)
   - the KDE settings from KDE.md
5. **`lodestar install` and the VM test,** repeated until a fresh install comes up
   clean.
6. **Migrate wandersail:** pre-wipe checklist, final backup, install, restore.
7. **Menadion, from home:** `lodestar plan` should show nothing to change. Then
   aconfmgr, chezmoi and `just` go. On the Windows side, rerun
   `Setup-Mpv.ps1` once, so `%APPDATA%\mpv` points to `modules\mpv\config`.

## 12. Implementation

- **Go.** Standard library first. The main dependencies are a YAML parser that
  reports errors with file, line and column (`goccy/go-yaml`), and a JSON
  Schema generator for Go types (`invopop/jsonschema`). It builds as a static
  binary (`CGO_ENABLED=0`).
- **Existing tools do the work.** lodestar calls the tool that owns each job:
  pacman, yay, makepkg, systemctl, kwriteconfig6, nft, cryptsetup, sgdisk,
  btrfs, snapper and bw.
- **Packaged like your other tools.** Its source sits in `modules/lodestar/pkg/`,
  so it upgrades itself when its source changes.
- **Size:** a few thousand lines.

## 13. Decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Names | tool `lodestar` (abbr `lds`), laptop `wandersail` | Cosmere: a lodestar is the device that carries its owner's controls into any machine; the Wandersail is Rysn's ship |
| 2 | Config language | YAML data, with a JSON Schema generated from lodestar's types; templates and hooks as escape hatches | completion and checks in VS Code; lighter than TOML; logic stays in Go where it can be tested |
| 3 | Package sources | one `packages` list, source resolved automatically; local packages from the modules' `pkg/` | moving a package between AUR and repo needs no edit; the plan shows the source |
| 4 | Removal | `apply` never removes packages, `prune` does; files and keys lodestar wrote are removed when undeclared | trying a package stays cheap; the repo stays the truth for config |
| 5 | Home files | copied; links opt-in (mpv, wallpaper dev) | apps can't scribble in the repo; drift sees edits |
| 6 | KDE | whole files for what KDE only reads, keys for what it writes; exceptions and window rules as lists lodestar owns; shortcuts in modules; `kde review` captures GUI changes | KDE's rc files hold state and machine-specific values; fixes the numbering clash; shortcuts are shared exactly per module |
| 7 | AUR | through yay | dependency resolution is yay's job |
| 8 | Tool source | in this repo (`modules/lodestar/pkg/`); `install.sh` builds it on the live USB; no published binary | one commit can change the tool and the config together; one command starts an install |
| 9 | Firewall | nftables, its own table; Docker's bridges trusted | Docker's rules survive; a port is one line in a module |
| 10 | Snapshots | snapper pre/post around every apply | a bad apply is one rollback away |
| 11 | Disk (wandersail) | 4 GiB ESP; LUKS2 with btrfs and a 32 GiB swapfile; passphrase unlock | hibernation without a second LUKS volume; TPM2 can be added later without reinstalling |
| 12 | Layout | a folder per host and per module, same layout; only `system/` and `home/` installed; a tool's package in its module's `pkg/`; mpv as a module | everything about one thing in one folder; nothing installed by accident |
| 13 | Tools with their own repo | `pkg: git:` with a pinned ref; the tool's PKGBUILD builds from that source; private repos wait for the first apply after install | the tool's repo stays the only copy of its packaging; updating is one line |
| 14 | Updates | `lodestar upgrade` wraps `yay -Syu` and rebuilds local packages; `rebuild-detector` instead of a hook of our own | a pacman hook can't build; the existing tool already warns |

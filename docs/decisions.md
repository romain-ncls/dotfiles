# Decisions

Why things are the way they are. Most of these were learned the hard way while
installing the home PC on 3 Oct 2026; the original install runbook is the
"Menadion Migration" artifact.

## Tooling

- **chezmoi for `$HOME`, aconfmgr for the system.** chezmoi handles per-machine
  templates and Bitwarden; aconfmgr's `save` lists every package, `/etc` file
  and service the repo does not know about, which is what keeps "every change
  is in the repo" checkable (`just drift`).
- **KDE settings as single keys, not files.** Plasma rewrites its rc files on
  every change (window geometry, timestamps, migration markers), so whole files
  would drift constantly. `home/.kde/*.tsv` holds only the keys changed on
  purpose; `scripts/kde-config` writes and checks them.
- **No secrets in the repo, even encrypted.** The repo is public and git
  history is permanent; an encrypted secret is only safe until its key leaks.
  Secrets stay in Bitwarden and are fetched at apply time.
- **Official Bitwarden CLI (`bw`) over `rbw`.** `rbw` is faster and has an
  agent, but it is third-party code handling the master password. chezmoi's
  `bitwarden.unlock = "auto"` removes most of `bw`'s session-token friction.
- **SSH keys per machine.** Nothing to restore on a new machine; a lost machine
  means revoking one key.

## Boot (home PC)

- **Limine on the shared ESP**, entries generated by `limine-entry-tool`
  (`limine-mkinitcpio-hook`), snapshot entries by `limine-snapper-sync`.
  Limine reads only FAT, so kernels live on the 4 GiB ESP.
- **`ENABLE_VERIFICATION=yes`**: a hash of `limine.conf` is enrolled into the
  loader. Any hand edit must be followed by `limine-update`, or Limine stops
  with a checksum error.
- **`FIND_BOOTLOADERS=no`**: otherwise the tool adds a *Systemd-boot* entry
  (dead after NixOS was removed) and an *EFI fallback* entry that chainloads
  Limine into itself.
- **`ENABLE_LIMINE_FALLBACK=yes`**: keeps `EFI/BOOT/BOOTX64.EFI` current. The
  MSI firmware sometimes boots that copy rather than the named entry.
- **`remember_last_entry: yes`, no `default_entry`, `timeout: 1`.** Remembering
  is what makes hibernation work on both OSes: an unattended power-on returns to
  the OS that was hibernated. Deliberate switching uses one-shot entries, which
  do not touch the remembered one. Not `timeout: 0`: the menu is the only way
  to reach the snapshot entries.
- **OS switching via `bootctl set-oneshot`**, not `systemctl reboot
  --boot-loader-entry=`: logind only accepts entries it finds as BLS files on
  the ESP, and Limine has none. The one-shot takes Limine's entry *id*
  (`Arch-Linux.linux`, `Windows-11`), not the menu title.
- **Rebuild with `limine-mkinitcpio`**, not `mkinitcpio -P`. The package
  replaces the stock pacman hook, so `/boot/initramfs-linux.img` is never
  updated and plain `mkinitcpio` does not update Limine's entries.

## initramfs (home PC)

`MODULES=(btrfs hid_logitech_dj hid_logitech_hidpp)`

- **No NVIDIA modules.** With them loaded from the initramfs (early KMS) and
  `NVreg_PreserveVideoMemoryAllocations=1`, the resuming kernel cannot freeze
  the GPU (`pci_pm_freeze returns -5`) and the hibernated image is discarded.
  Loaded later from the root filesystem, resume works. Cost: a brief mode switch
  at boot. `nvidia_drm.modeset=1` stays on the kernel command line.
- **Logitech receiver drivers.** Without them `hid-generic` claims the G305's
  Lightspeed receiver at ~5 s and `logitech-dj` takes over at ~12 s; on about
  2 boots out of 3 the receiver never re-announced the mouse.

## Hardware (home PC)

- **NVIDIA**: `nvidia-open-dkms`; `options nvidia NVreg_PreserveVideoMemoryAllocations=1`
  (check `journalctl -b | grep 'ignoring bad line'` is empty after editing);
  `nvidia-suspend/hibernate/resume.service` enabled.
- **Flat mouse acceleration for every mouse.** KDE stores it per device; there
  is no global switch, so `scripts/flat-mice` writes it for every mouse seen.
- **C: mounted at boot with the new in-kernel `ntfs` driver** (kernel 7.2). It
  mounts a hibernated or dirty volume read-only instead of refusing it. If it
  misbehaves, `ntfs3` is the fallback.

## Not in the repo yet

- **VS Code** settings and extensions stay in VS Code Settings Sync for now,
  until they are cleaned up; then they move here (settings.json via chezmoi,
  extension list installed by a run script) and Sync gets turned off. Install
  `visual-studio-code-bin` (AUR, Microsoft build): several extensions are only
  on Microsoft's marketplace.
